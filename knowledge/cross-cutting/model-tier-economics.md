# Model tier economics — inherit the session model by default, configure tiers via models.yaml

Domains: agents, skills, cli, auto-mode

**Why this matters.** Belmont's pipeline amplifies model error rates into token cost: a failed milestone re-enters implement → verify → review (→ debug), and every retry reloads the full feature context (PRD/PROGRESS/NOTES can run to hundreds of KB) across 4–5 agents. The marginal cost of a smarter model on the first pass is small compared to the cost of one extra pipeline re-run. So when a user *does* assign tiers, the right bias is toward the high tier for any agent whose mistakes cascade. But that is a *recommendation about how to configure*, not a reason for Belmont to hardcode a model into every agent file — a tool other people install must not silently override the model the user chose for their session.

**Invariant.** Belmont agent files (`agents/belmont/*.md`) pin **no** `model:` frontmatter. A dispatched sub-agent therefore inherits the **session model** — the model the orchestrator is running on (the interactive Claude Code session, or the headless `claude -p` process in auto mode). Per-feature `.belmont/features/<slug>/models.yaml` is the *only* place a model is pinned per agent (configuration over convention): the skills translate each listed tier into the dispatch tool's `model:` parameter, which overrides the inherited session model. This means "run Belmont on a strong model and the whole pipeline follows; downgrade deliberately per agent via `models.yaml`." Cost reduction happens through (a) deliberate per-feature tiers in `models.yaml` — primarily `low` for mechanical, low-blast-radius work — and (b) input-side trimming (MILESTONE architecture, progressive-disclosure references, `/belmont:cleanup`, optional RTK proxy). **Exception (auto mode only):** the Go CLI forces the high tier for planning and reconciliation via the `planningTier` / `reconciliationDefaultTier` constants — both are high-blast-radius and not per-milestone — independent of any frontmatter.

**How it's enforced.** Absence of `model:` in `agents/belmont/*.md`; the documented inherit-then-override chain in `skills/belmont/_src/references/models-yaml-format.md` (Tier economics + Fallback sections), `_partials/dispatch-strategy.md` (Model Tier Overrides), and the `implement` / `verify` / `tech-plan` skills; tech-plan heuristics steer per-feature tier choices with the cascade rule ("when torn between two tiers for an agent whose mistakes trigger pipeline re-runs, take the higher one"). The `modelTiers` registry maps tiers → model IDs only; *which* tier an agent gets is policy that lives in `models.yaml` where users can see and override it.

**Failure mode if you break it.** Three, and the third is the one that shipped for months:
- *No dispatch at all, so nothing to override:* `dispatch-strategy.md` told the orchestrator to check for `Task` and `TeamCreate` **by name**. Claude Code's dispatch tool is `Agent` and teams no longer exist, so the decision tree walked past both dispatch approaches and selected the sequential-inline fallback — on the tool Belmont is primarily used with. Under that fallback there is no dispatch call, so there is nowhere to put `model:` and **every tier in `models.yaml` was inert**, silently: the skill never claimed to have applied them and `models.yaml` has no runtime validation. Fixed in #45 by keying the check on `Agent` (accepting `Task` as its older name) and by requiring the orchestrator to state which approach it selected. The general lesson is that a tier mechanism riding on a dispatch call is only as live as the availability check in front of it, and nothing was auditing that check.
- *Silent downgrade:* commit `a4fe0ea` set `implementation-agent.md` to `model: sonnet` as a side effect of introducing per-feature tiers, while README/docs still said Opus — a hidden default nobody chose. (Note: because every skill dispatches sub-agents as `subagent_type: "general-purpose"` and feeds the agent file as a *prompt*, that frontmatter was never actually read at dispatch time — so the value mismatch was pure misdocumentation, which is its own hazard.)
- *Silent override:* PR #18's first cut flipped all six files to `model: opus` to "fix" the above. That re-introduces a convention that overrides the user's session choice on paper, and still relies on frontmatter nothing reads. Both were rejected in favour of pinning nothing and letting `models.yaml` be the single, visible override point.

**Don't re-do.**
- *"Hardcode `model: opus` (or any model) in agent frontmatter so the pipeline always runs high."* — rejected. (a) The frontmatter is not honoured at runtime: sub-agents are dispatched as `general-purpose` and the agent file is read as a prompt, and the Go CLI never parses agent frontmatter for the model — so the pin is documentation theatre. (b) Even if honoured, it would override the model the user deliberately chose for their session. Configuration over convention: pin via `models.yaml`, default to inherit.
- *"Default to the mid tier because it's cheaper per token."* — rejected as a *configuration* recommendation. In reasoning mode the end-to-end discount is ~10%, and elevated rework makes it net-negative; for cascade-prone agents prefer `high`. (June 2026 benchmarks; re-measure before leaning on this.)
- *"Encode the tier policy in Go (`modelTiers`)."* — rejected. The registry maps tiers → model IDs; the policy of which tier an agent gets belongs in `models.yaml` where it's visible and overridable.
- *Caveat to document, not a thing to re-do:* in auto mode a **partial** `models.yaml` (e.g. `implementation: low` but `codebase` unset) makes the headless session low-tier for that wave, so the unset sibling agents inherit low too. This is the expected, intended consequence of "configuration over convention" — set the siblings explicitly if you want them higher.

**Evidence.** The rework economics that justify biasing *configured* tiers high: Artificial Analysis Intelligence Index (June 2026): Opus 4.8 score 61.4 / $4,686 eval cost / 63.7 tok/s vs Sonnet 4.6 (reasoning) 52 / $4,206 / 45.4 tok/s — a ~10% end-to-end cost gap, not 40%. Model-attributed rework analysis of two production Belmont projects (~2,325 and 50+468-archived-milestone commit histories): per-model rework ratios 29.2% (Sonnet) vs 19.7% (Opus); fix-follows-feature clustering 21.6% vs 14.4%. The runtime mechanics (general-purpose dispatch ignoring agent frontmatter; Go resolving the model from `models.yaml` tiers / `planningTier` / `reconciliationDefaultTier` only) were confirmed against `_partials/dispatch-strategy.md` and `cmd/belmont/toolexec.go` (`resolveModelFlags` / `tierForAction`) on 2026-06-04; Claude Code's "omitted `model:` ⇒ inherit main-conversation model" behaviour confirmed against the current subagents docs the same day.
