# PROGRESS.md Parsing: One Definition Per Concept

**Domains:** cli, state, auto-mode

**Why this matters.** PROGRESS.md is the single source of truth for all state, and it is read by at least eight independent pieces of code — the parser, the scope-guard snapshot, the evidence guard, the merge-conflict resolver, the post-merge sync, `reverify`, the skip path, the FWLUP scans. Each one historically re-implemented the structural questions "what does this marker mean?" and "where does the milestones region end?" with its own inline regex or string test. **Two shipped issues came from exactly that duplication, and in both cases every copy was wrong in the same way, so no amount of cross-checking between them would have caught it.**

The failure signature is always the same: information disappears and nothing errors. That is worse than a crash, because the file still looks fine and `belmont validate` still exits 0.

## Invariant

- **`canonicalMarker(marker) (taskStatus, bool)`** is the only definition of what a checkbox marker means. Derived helpers — `markerRank`, `markerIsVerified`, `markersDiffer` — route through it. Nothing compares a raw marker byte, and nothing tests two markers for equality with `!=`: `[v]` vs `[V]` differ as bytes and not as states, and `diffScopeViolations` read that as an out-of-scope flip, reverted the line, amended the revert into the agent's commit and injected a correction for an edit nobody made.
- **Adding a marker re-reads every file that already exists.** `[-]` and `[V]` were unrecognised — loud, blocking, un-actable — and now mean withdrawn and verified, with no migration. Every reader carrying its own classification quietly changed behaviour on upgrade: `resolveProgressConflict` revived withdrawals (and could mint a `[v]` no guard audits), `mergeProgressState` overwrote a worktree's completion or blocker in silence, an all-withdrawn milestone rendered `[v]` verified, and the listing view counted dropped work as awaiting verification. Before extending the set, grep every consumer of `markerRank` / `taskStatePriority` for its special cases and ask what the new marker means to a file written before it existed.
- **`isSectionBreak(line) bool`** is the only definition of where the milestones region ends. It matches a level-2 ATX heading **at column zero only**; indentation is never trimmed first.
- **`parseTaskID(text) (id, name, ok)`** is the definition of a task's **identity** — the `<ID>:` token a commit-evidence lookup and a repair finding key on. It accepts the template shape (`P\d+-…`, first in the alternation so nothing that parsed before parses differently) plus an **uppercase-initial** hyphenated identifier ending in a number, which is what people write by hand: `FWLUP-SWEEP-1`. Both guards on the second alternative are load-bearing. The trailing `-\d+` keeps `Note:`, `Fix the login:` and `re-run:` out; the uppercase initial keeps `utf-8`, `sha-256` and `base-64` out, and that one is not cosmetic — a prose token accepted as an ID means a commit merely *mentioning* it becomes evidence, and the mechanical tier auto-writes `[x]` for work nobody did.
- **The file side and the commit side must accept the same ID shape.** `taskIDShape` (state.go) is shared by `taskIDRe` and by `commitNamedTaskIDs`, which harvests maximal tokens out of commit messages and filters them through `taskIDShapeRe`. Widening one without the other is a shipped bug in itself: with `parseTaskID` widened and the commit index still `P\d+-`-only, every `[v]` carrying a hand-written ID entered `auditVerifiedWithoutEvidence` and was reported as unproven **while `lookupCommitEvidence` found a commit naming it verbatim** — and the remedy the report offers is to demote a commit-backed verified task. Harvest-then-filter rather than embedding the shape: `feat-P1-M1-1` stays one token and so cannot read as a mention of `P1-M1-1` (which `lookupCommitEvidence` also rejects), whereas a right-boundary group would drop the second ID in `P1-M1-1 P1-M1-2`.
- **Two readers stay wider on purpose, and two more are not converted at all.** `parseProgressSnapshot` and `revertEvidenceMissing` match `(\S+?):` because they answer a different question — "what token identifies this line inside its milestone block", for flip detection — where matching too little drops the line from `TaskStates` and lets an out-of-scope flip past the scope guard unseen. Documented at both call sites; narrowing them to reduce the regex count would weaken a runtime guard. Separately, `mergeProgressState` (worktree.go) and `resolveProgressConflict` (merge_conflict.go) still compile their own `P\d+-[\w][\w-]*`, so a hand-written ID is **not** matched across a worktree merge — the pre-existing "no parseable ID → left as the worktree wrote it" limitation, unchanged by the widening but now reachable by a task that is first-class everywhere else. Converting them changes merge behaviour for files already on disk and needs its own eval; until then, say four-of-six, not "all readers".
- **Detection without repair is half a fix.** A file this parser refuses is a file its owner cannot move, so `belmont repair` closes the loop with commit evidence and a code read — never by asking what a marker meant. See [progress-repair.md](progress-repair.md).
- **Nothing is dropped in silence.** An entry Belmont cannot place is surfaced, not discarded: an unreadable marker becomes `taskUnknown` (counted separately, rendered `[?]`, `belmont validate` exit 1), and a task line outside every milestone is reported by `orphanedTaskLines` → `detectOrphanViolations`.
- **The marker set must be able to express every state a task can be in.** `[-]` withdrawn exists because its absence *is* issue #27: Belmont had no way to say "we decided not to do this", so a user invented `[-]`, and every unrecognised marker parsed as todo. Repair tooling does not fix that — without a legal way to express withdrawal the next person invents a marker too. Withdrawal is a **state, not a deletion**: `mergeProgressState` takes the worktree as base and carries master's missing lines back in, so a deleted task is resurrected by the next sibling sync in *either* direction (proved by `TestWithdrawalSurvivesTheMergeThatDeletionDoesNot`). A marker survives, and — like `[!]` — withdrawal wins from either side, so a stale worktree cannot silently revive dropped work. The reason goes in `## Decisions Log`; a marker cannot carry why. Letter markers are case-insensitive (`[X]`, `[V]`).
- **Ambiguous structure is refused, not guessed.** A repeated `### M<n>:` heading makes every milestone-keyed lookup resolve arbitrarily. `parseProgressSnapshot` records it in `DupIDs`; `runScopeGuard` and `runEvidenceCheck` both decline to run and say why; `detectViolations` raises `duplicate_milestone_id`; and `requireUnambiguousMilestones` refuses to start `belmont auto` at all, on **every** path and without an override. Same policy as a duplicated task ID in `mergeProgressState`.
- **A report about a malformed file must be enough to fix it.** `renderValidationReport` prints the expected structure — header shape, task-line shape, the marker set, where a column-zero `## ` ends the region — and tags each violation with a remedy: `needs_evidence` (the answer is in the repository) or `tech_plan` (structural, and the scope guard reverts anyone else who tries). **Never cite a path under `skills/belmont/_partials/`**: it is build-time source that `belmont install` does not write, so in a consuming project it is a dangling pointer. That applies doubly to `injectScopeGuardSteering`, whose text is prepended to the next phase's prompt as an instruction.
- **Surfacing something is not the same as blocking on it.** Violations carry a `Severity`. `severityError` means the loop cannot proceed correctly and stops it; `severityWarning` means information that must not be lost but breaks nothing — currently just `task_outside_milestone`. `splitBySeverity` treats an unset severity as blocking, so a new rule that forgets the field fails loudly rather than being silently downgraded.

## How it's enforced

In `cmd/belmont/state.go`:

- `canonicalMarker` / `markerRank` / `markerIsVerified` — marker semantics. Callers: `parseMilestones`, `resolveProgressConflict`, `mergeProgressState`, `resetVerifiedTasks`, `findEvidenceMissingFlips`, `revertEvidenceMissing`.
- `isSectionBreak` — region boundary. Callers: `parseMilestones`, `orphanedTaskLines`, `skipMilestoneInProgress`, `rebuildAfterScopeGuard`, `parseProgressSnapshot`, `revertEvidenceMissing`, `mergeProgressState` (both walks **and** its duplicate-ID counter), `resolveProgressConflict` (both the `theirsStates` scan and the `ours` rewrite), `resetVerifiedTasks`, `pendingTasksInRange`, `fwlupTasksInRange`.
- `parseTaskID(text)` / `taskIDShape` / `taskIDShapeRe` — task identity. Callers: `parseMilestones`, `orphanedTaskLines`, `taskIDsClaimedElsewhere` (repair.go), and `commitNamedTaskIDs` (guards.go) via `taskIDShapeRe`. Deliberately **not** `parseProgressSnapshot` / `revertEvidenceMissing`; not *yet* `mergeProgressState` / `resolveProgressConflict` — see the invariant above before "fixing" either, and run `grep -n 'P\d+-' cmd/belmont/*.go` rather than trusting this list.
- `orphanedTaskLines(progress)` — task lines outside any milestone. Surfaced by `renderStatus` and by `detectOrphanViolations` (wired into `belmont validate` and auto's startup lint). Its advice is **conditional**: a task whose ID names a milestone the file already has is told so and pointed at `belmont repair`; only a genuinely unattributable one gets the destination rule. Unconditional advice to "move it under its `### M<n>:` heading" is what closed the guidance loop in issue #34.

**Verify that caller list with `grep`, not by reading a commit message.** The first version of this entry listed `rebuildAfterScopeGuard` as a caller and it was not one — the commit that claimed to convert "all five readers" converted four, missing exactly that one, and this entry repeated the claim. Three later commits then built on top of a seam that nobody had checked. `grep -n 'isSectionBreak' cmd/belmont/*.go` against `grep -n '"## "' cmd/belmont/*.go` takes seconds and is the only trustworthy answer. The follow-up commit that fixed the seam then miscounted the miss in the other direction — worth knowing that a wrong count survived two commit messages, which is why the grep is the rule and not the prose.

Tests: `cmd/belmont/marker_readers_test.go`, `cmd/belmont/section_break_test.go`, `cmd/belmont/region_scope_test.go`. Each has a control that fails when the defect is reintroduced, including `TestSnapshotAgreesWithParserOnIndentedHeading` and `TestRebuildAgreesWithSnapshotOnBlockBoundary`, which pin the parser, the scope-guard snapshot and the guard's *rebuilder* to the same answer. The controls are mutation-tested: reintroducing any of the region-blind walks fails at least one named test.

## Failure mode if you break it

- **Inline the check "just here".** That is how both bugs shipped. Issue #27: five readers each compared marker bytes; `[V]` counted as verified everywhere while being invisible to the evidence guard. Issue #31: five readers each did `strings.HasPrefix(strings.TrimSpace(line), "## ")`, so a heading indented inside a task's own write-up body ended task collection for the rest of the file — 85 of 541 tasks invisible on a real project, including outstanding `[ ]` and `[!]` work, `Status: Complete`, `validate` exit 0.
- **Trim before testing a structural prefix.** Indentation is semantic in Markdown. `  ## Foo` under a list item is that item's continuation, not a heading.
- **Treat "can't parse this" as a default state.** Guessing `todo` for an unknown marker is what made #27 schedule cancelled work for implementation.
- **Let the parser and the scope-guard snapshot diverge.** They must agree on region boundaries or the guard reverts the wrong lines.
- **Convert *some* of the readers and describe it as all of them.** The half-conversion is worse than none, because the two halves then disagree. The snapshot decides where a milestone block *ends*; the rebuilder decides which post lines that block *replaces*. When only the snapshot was converted, an out-of-scope revert emitted the pre block whole and then re-emitted post's leftover tail below it: the task line appeared twice with contradictory markers, and **the illegal flip the guard had just detected survived on disk** while the run logged `✓ reverted 1 violation(s)`. Re-applying it doubled the duplicates again. In the mirror case (`##` + tab, which `isSectionBreak` accepts and a literal `"## "` test does not) the replacement ran past the real region end and deleted `## Session History` outright. A boundary mismatch is not a missed revert — it is active corruption written to disk and amended into the agent's commit.
- **Region-scope the reads but not the writes.** `resolveProgressConflict` builds its state map last-occurrence-wins, so an unscoped walk let a task-shaped line under `## Session History` shadow the real one in both directions: a quoted `[v]` **minted a verified flip with no commit evidence** (and `runEvidenceCheck` only ever inspects a post-*phase* file inside the worktree, never a post-*merge* file on master, so nothing audits it), while a stale quoted `[ ]` hid a genuine `[x]` and the completion vanished under a green "conflicts auto-resolved". Any map keyed by task ID needs the region gate, and so does the loop that writes the result back.
- **Count with a different rule than you merge with.** `mergeProgressState`'s duplicate-ID refusal counted task-shaped lines document-wide while both of its walks honoured the region. A sibling logging `- [x] P1-M1-1: done, commit abc123` into the history therefore made the real in-region task look ambiguous; the refusal dropped master's completion and the warning told the user to de-duplicate an ID that occurs once.

## Don't re-do

- **Make `isSectionBreak` accept indented headings "for robustness".** It is the bug. A column-zero `## ` genuinely ends the region — `## Session History` and `## Decisions Log` follow the milestones in every real file — so the boundary must stay, only the trimming goes.
- **Count orphaned tasks into their preceding milestone.** Considered for #31 and rejected: past a real column-zero break they are genuinely outside the region, and silently adopting them would make `## Session History` entries into tasks. Report them instead.
- **Suppress a merge carry-over because the other side "already has" the ID somewhere.** Tried and reverted within one commit. Keying `mergeProgressState`'s carry-over off every occurrence — in-region *and* orphaned — looks like duplicate-prevention and is state loss: when a worktree holds an ID only as an orphan (a fork-stale line stranded behind a heading its agent wrote, or a sibling's completion quoted into a log), master's in-region copy is the only counted one, and skipping it deletes the task from the only document that carries it. Carry it in and warn. Splicing is safe precisely *because* `countIDs` is region-scoped — an in-region line plus an orphan sharing its ID is not a duplicate, so the next sibling merge will not refuse it. The carry-over gate must be the in-region set alone.
- **Make every new finding block the loop.** The never-drop-in-silence rule says *report* it, not *refuse over* it. Orphan detection shipped as a hard violation and that made an upgrade break working projects: a `- [ ]` bullet in a retro under `## Session History` is a note, not work, and it aborted `belmont auto`. Ask what the loop cannot do if the finding is real. An unrecognised marker makes its milestone permanently un-completable and colliding milestone IDs switch the guards off — those block. A line that is merely uncounted does not.
- **Narrow the guards' `(\S+?):` to `parseTaskID` "so there is one regex".** The regex count is not the invariant; the *question* is. Identity readers must agree with each other, and the guards' token match must agree with its own rebuilder. Collapsing the two makes the scope guard stop tracking any task line whose leading token is not a conforming ID, and an untracked line is an unguarded one.
- **Widen `parseTaskID` to the guards' pattern instead.** The mirror mistake, and the more tempting one because it looks like strictly more coverage. `- [ ] Note: chase this` would acquire the "task ID" `Note`, which then gets a commit-log lookup and can be reported as claimed by a sibling feature. The same argument is why the second alternative demands an uppercase initial: `utf-8` and `sha-256` are shaped exactly like a hand-written ID, and accepting one means a commit that merely mentions it lets the mechanical tier auto-write `[x]` for work nobody did. `TestParseTaskIDAcceptsHandWrittenIDsWithoutEatingProse` fails in both directions for this reason.
- **Use a Markdown library.** Belmont's CLI is deliberately stdlib-only (`AGENTS.md`), and the file is a fixed, small dialect. A parser dependency buys correctness on constructs Belmont does not use and costs the zero-dependency property.

## Evidence

- Issue #27 — `[X]`/`[V]`/`[-]` all parsed as `todo`; a completed task was offered as *Next Individual Task*. Reproduced before/after with the harness: before offers `P1-M1-2 - capital X` and `validate` exits 0; after offers `None` and exits 1.
- Issue #31 — the reporter's exact fixture yields 2 of 4 tasks before, 4 of 4 after; `Status: Complete` → `In Progress`, with the `[!]` blocker surfaced.
- Both were found by a user on a real project, not by any check in this repo. The class is invisible to tests that only exercise well-formed fixtures — every fixture in the suite before #31 used column-zero headings.
- The controls only count if they can fail. Before the caller list was completed, six mutations passed the whole suite — including severing orphan detection from `belmont validate` and from `belmont status`, i.e. reproducing #31's exact "validate exits 0" symptom. Two tests were vacuous for the regression they named: one used a markdown table where the fixture needed a task-shaped line, and a resolver test's two sides stopped colliding, so git merged them cleanly and the resolver under test was never called. **A conflict fixture must be asserted to have conflicted** — never `t.Skip` when the resolver declines, or the test passes forever without running anything.

## Verification

Every rule above is mutation-tested. Reintroducing any region-blind walk, severing any wire from orphan detection to a user-visible surface, or reverting the carry-over gate fails at least one named test. Re-run that check after touching this area: back up `cmd/belmont/`, apply each mutation, `go test ./cmd/belmont`, restore. A mutation that survives is a missing control, not a passing suite.
