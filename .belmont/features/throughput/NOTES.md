### Debugging
- **`git branch -r --no-merged main` over-reports in a rebase-heavy repo.** It compares ancestry, so a rebased-and-landed branch still lists as unmerged. 21 of Belmont's 35 "unmerged" branches were fully or effectively landed. Use `git cherry -v main <branch>` (patch-equivalence: `-` = already upstream, `+` = outstanding), then hand-check the residue — patch-ids are defeated by context drift, which produced false positives on `feat/maintenance-ci` and `fix/worktree-git-excludes`.
- **`git rev-parse "main:$path"` echoes the argument back when it cannot resolve it**, so a missing file reads as present. Use `git rev-parse --verify --quiet` or `git cat-file -e`. This silently inverted a whole triage pass.
- **Two-dot `git diff main..<branch>` is meaningless when main is far ahead** — it reports main's own additions as the branch's deletions (every branch looked like a 30,000-line deletion against a 157-commit-ahead main). Use three-dot `main...<branch>` for a branch's own changes.
- **A cherry-picked commit still shows as `+` under `git cherry` when the pick conflicted.** `1129cf84` was picked onto `main` as `24db490`; because the conflict resolution changed its context lines, its patch-id changed, and `git cherry -v main origin/feat/maintenance-ci` still lists it as outstanding. So `git cherry` cannot confirm your own recovery either — grep the file for the content.
- **Identify a leftover commit from `git show <sha>`, never from the branch's diff against `main`.** The original triage named the two leftovers by picking two plausible changes out of `git diff main...<branch>`. Both named changes are genuinely on `main` — they just are not what either leftover commit contains. A three-dot diff shows every change the branch made since the merge-base, including ones `main` has independently, so it cannot tell you which change belongs to which unlanded SHA.

### Pattern
- **The torn-write window is huge, not theoretical.** A negative control (same concurrent harness, old `os.WriteFile`) observed a **0-byte read on every run within 0.02s** against 300 rewrites. `os.WriteFile` truncates then writes, and Belmont's readers parse an empty `PROGRESS.md` as zero milestones without erroring. Always pair an atomicity fix with a negative control — a race test that cannot fail proves nothing.
- `os.CreateTemp` creates **0600**. Any temp-file-then-rename helper must `Chmod` to the caller's perm before the rename or it silently tightens every file it touches from 0644.
- Rename **replaces** a symlink where `os.WriteFile` **follows** it. Two callers depend on the old behaviour (`writeReconciliationResolution`, `copyFile`) and both resolve symlink-ness above the call — convert the final write only, never the whole function.

### Pattern
- Reuse `parseMilestones` + `taskBodyEnd` for anything that needs a task's body extent — `blockers.go:taskDetail` already composes them. Do not write a third line-scanner.
- **An indented line is not the same thing as a movable byte, and the gap is measurable.** `repo-3/feat-015` has 84,593 B of indented lines but only 77,976 B of detail: `taskBodyEnd` claims a line only if it lies in a *task's* body, so indentation beneath a heading stays in the index. Quote the one the sentence is actually about — "has no indentation" and "gains nothing from extraction" are different claims, and conflating them is what `P0-M1-FIX-6` had to retract.
- **The gap runs in both directions, so indentation is not an upper bound.** `censusFeature` claims every line index from a task line to `taskBodyEnd`, blank lines inside a body included — and a blank line is not an indented line. Where a register has no indentation outside a task body, moved is *at least* indented, and exceeds it whenever a task body contains a blank line: `repo-3/feat-070` moves 141,001 B against 140,957 B indented, the 44 B being its 44 in-body blank lines at one newline each (measured 2026-08-18, `P0-M1-FIX-8`) *(clause corrected by `P0-M1-FIX-10`, 2026-08-18 — first written as "exceeds", the measured relation is "at least")*. - When summing what a task body would move, record **which line indices** move rather than summing per-task lengths: a nested task bullet lies inside its parent's body *and* is a task itself, so the naive sum double-counts.

### Pattern
- **`loopConfig` has two roots, not one.** `Root` follows the worktree under `runAutoParallel`; anything that must outlive the wave must not. `worktreeLoopConfig` (auto_parallel.go) is now the single place both worktree sites derive the child config, so the question "which root does this resolve to?" is asked once. Ask it of any new path root added to `loopConfig`.
- **`RunID` must be minted by the orchestrator, not by `runLoop`.** `runLoop`'s fallback keys off its own start time, which is right serially and wrong for a wave — N worktrees produce N run IDs for one invocation, and `belmont metrics` aggregates per run. Seeded in `runAutoParallel` and `runAutoMultiFeature` before any worktree exists.
- **O_APPEND concurrency safety is per `write()` call, not per file handle.** Measured 2026-08-18, macOS/APFS, 16 goroutines x 400 records to one file: `appendMetricsRecord`'s single `f.Write(append(data, '\n'))` produced 6400 intact lines, 0 unparseable. A negative control splitting the payload and the newline into two writes lost ~47% of its lines and left ~1850 unparseable **on every run**. So the shared-append path is safe, but only while the record and its newline stay in one write — no `bufio.Writer`, no second `Write`. The failure class is a garbled line, not a torn file, which is categorically different from what `writeStateFile` exists to prevent.
- **A serial-path test passes either way here.** `recordPhaseMetrics` with `MetricsRoot` unset behaves exactly as before the fix, so only a test that sets `MetricsRoot != Root` can detect the defect. Confirmed by reverting the fix and watching the three worktree tests fail and the serial test pass.

### Discovery
- **codex's `input_tokens` INCLUDES `cached_input_tokens`, and codex's `turn.completed` usage is SESSION-CUMULATIVE, not per-turn.** Verified 2026-08-18 against codex-cli 0.147.0 with a three-turn session (`codex exec --json`, then `codex exec resume --last --json` twice): input/cached read 17308/4480 → 34647/21248 → 52003/38016, i.e. per-turn 17308/4480, 17339/16768, 17356/16768. Claude is the opposite — `input_tokens` is the uncached remainder, and the whole prompt is `input + cache_creation + cache_read`. What the run did **not** settle: whether cache *writes* are also inside codex's `input_tokens` (`cache_write_input_tokens` was 0 on every turn). Not needed — the aggregation rule keys off the definitions differing at all.
- `codex exec resume` rejects the top-level `-s/--sandbox` flag that `codex exec` accepts; drop it when resuming.

### Pattern
- **Refuse, don't normalise, when vendor semantics diverge.** `summariseMetrics` now aggregates `Input` only across records sharing one `input_semantics`, and reports `null` + a stated reason + a per-tool breakdown otherwise. Normalising to a tool-independent quantity was the alternative and was rejected: it is correct only while every tool's semantics are known *and stay known*, so a new tool or a vendor redefinition silently re-arms the same wrong-but-plausible baseline. Records with no recorded definition are summable only with the same tool's — unknown never merges into a known definition.

### Pattern
- **Coverage belongs in the artefact, not in the terminal.** The census's silent skip could have been "fixed" with a stderr warning, and that would have reproduced the defect: the numbers get copied into other documents and the caveat does not — which is literally what happened to 138/65. The fix that holds is (a) refuse by default, (b) make the opt-in explicit, and (c) put the coverage facts *inside* the report (`roots_walked`, `unreadable_roots`, `coverage_complete`, plus a banner above **and** below the table) so a reader of the output can tell what was walked without re-running anything.
- **A signature change makes "revert and watch it fail" prove the wrong thing.** Reverting `P0-M1-FIX-7` wholesale would have broken compilation, so the tests would "fail" as a build error rather than as an assertion. Demonstrate by reverting only the behavioural line — re-inserting `if os.IsNotExist(err) { continue }` while keeping the new signature — and confirm the assertions themselves fail. Two of the four new tests fail that way; the other two cover the complete-walk and unlistable-directory branches and pass either way, which is expected and worth saying out loud rather than presenting four tests as four proofs.

### Pattern
- **An "ignore it" fix is itself a tree-dirtying write.** `.gitignore` is a *tracked* file, so `ensureGitignoreEntry` on the auto path trades an untracked `.belmont/metrics/` for a modified `.gitignore` — and `requireCleanWorkingTree` refuses the next run either way. Three orderings, only one survives: before the clean-tree check turns a command that worked yesterday into one that refuses to start; after it but uncommitted just moves the dirt; after it *and* committed (one path, pathspec-scoped, at most once per repo) is the only one where a failure is survivable. Ask of any new "just gitignore it" fix whether the file it writes is tracked.
- **A test whose fixture's own last commit touches the file under test passes with the fix reverted.** `TestAutoPreflightCommitsOnlyTheGitignoreItWrote` first asserted `git diff --name-only HEAD~1 HEAD == ".gitignore"` — true of the fixture's *setup* commit, so it passed with `ensureMetricsIgnored` deleted. Capture `rev-parse HEAD` before the call and assert it moved. Same class as the NOTES rule above it: run the revert, and read *which* tests failed rather than that some did (here 2 of 6 fail on revert; the other four are guard tests — idempotence, dry-run, dirty-tree refusal, non-git — which assert the fix does *not* act and pass either way by construction).

## Root Cause Patterns

### [2026-08-18] Pattern: a new state write was only ever exercised on one of two execution paths
**Issue**: Every metrics record is written to `cfg.Root`, which `auto_parallel.go` sets to the worktree path — so the instrumentation the whole feature is judged by produces nothing in parallel-wave mode, the mode this feature itself will run in.
**Root Cause**: Belmont has two execution paths for the same loop (serial `runLoop`, and `runAutoParallel` per worktree). The repo documents this in `knowledge/cross-cutting/dual-invocation-paths.md`, and the codebase scan explicitly named that rule for P0-2 — but the rule exists only as prose, so applying it depended on the implementer recalling it at the moment of writing the path expression. Nothing mechanical gates it.
**Prevention**: Any new write under `.belmont/` must be exercised on **both** paths before the task is marked done, with a test that pins the worktree case specifically. If a value is a path root, ask which of the two roots it resolves to under `runAutoParallel` — the answer is usually not the one you want.
**Source**: M1 / P0-2

### [2026-08-18] Pattern: a census derived its own scope instead of taking the spec's enumeration
**Issue**: The extraction census walked five roots, but not the five the PRD names — `repo-2` (31 feature dirs, 18 live registers) was never measured, so the denominator is 138/65 instead of 168/82.
**Root Cause**: The scope was assembled from what was conveniently to hand rather than from the PRD's explicit list, and `runCensus` swallows an unreadable root (`os.IsNotExist → continue`). An incomplete walk is therefore indistinguishable from a complete one at every level — no error, no warning, just a smaller number that looks like a finding.
**Prevention**: When a spec enumerates its subjects, use that enumeration verbatim as the input list and **fail loudly** on any member that cannot be read. A missing input must never degrade silently into a smaller denominator.
**Now enforced in code (`P0-M1-FIX-7`)**: `runCensus` collects every root it cannot read and returns an error naming them; `--allow-unreadable-roots` is the only way past it, and the report then carries `roots_walked` / `unreadable_roots` / `coverage_complete` and prints `Coverage: INCOMPLETE` above the figures and again below them. The first half of the rule — taking the PRD's enumeration — remains a human discipline; only the "fail loudly" half is mechanical.
**Source**: M1 / P0-4

### [2026-08-18] Pattern: a measurement was used to correct the spec before it was known to be complete
**Issue**: CENSUS.md declares *"the PRD's phrase 'the other 83' does not match disk"* — but the PRD's figure reproduces exactly once the omitted repo is included. The PRD was right; the correction was the error. Separately, "three of the five contain no indented lines at all" is wrong (two do), and was copied verbatim into four files, one of them directly beneath a human-gated escalation the owner will read when deciding whether to restructure the waves.
**Root Cause**: Same shape as the numeric-drift pattern already recorded in `framework-evaluation`'s NOTES: a derived figure was restated across documents instead of living in one canonical place, and it was trusted enough to contradict the spec before its own coverage was checked.
**Prevention**: Before contradicting a spec's number, prove your measurement covers the spec's full scope. State a measured figure once, in one file, and have every other document link to it rather than repeat it — a wrong number repeated four times is four times as expensive to retract.
**Source**: M1 / P0-4

### [2026-08-18] Pattern: triage verdicts written from summary evidence rather than from content
**Issue**: `origin/feat/maintenance-ci` was verdicted *abandon* on the claim that both leftover commits are already on `main`. One is not — `1129cf84`'s 23-line `--max-parallel` gotcha is absent, and the triage mis-describes it as a different change entirely. A second abandon verdict gives a reason (`main` "already scopes the sync per milestone") that is simply untrue of `main`'s code.
**Root Cause**: Verdicts were formed from commit counts and plausible-sounding mechanisms rather than by reading the specific content in question. `git cherry` tells you a patch-id is unmatched; it does not tell you whether the *content* landed by another route, and a mechanism that sounds right is not evidence that it exists.
**Prevention**: An "already landed" verdict must name the commit **and** show its content present on `main` (`grep` the heading, diff the file). An "abandon" reason must name the superseding mechanism on `main` and cite the lines that implement it. A destructive recommendation carries a higher evidence bar than a keep.
**Source**: M1 / P0-13

### [2026-08-18] Pattern: identically-named fields from different vendors normalised without recording their semantics
**Issue**: `summariseMetrics` sums `Input` across tools whose `input_tokens` differ in meaning — claude's excludes cache reads, codex's includes them.
**Root Cause**: Two schemas share a field name but not a definition. The per-tool parsers are individually correct (and the field names are *not* transposed — that trap was avoided and pinned by tests), but the divergence was recorded only in a comment at the parse site, not carried to the aggregation boundary where it actually bites.
**Prevention**: When ingesting the same-named field from different vendors, record the semantic **at ingest** as data, not as a comment, and refuse to aggregate across sources whose semantics differ. A summary that silently mixes definitions produces a plausible wrong number — the exact failure mode the "never estimate" rule exists to prevent, arriving by a different door.
**Source**: M1 / P0-2

## Root Cause Patterns

### [2026-08-19] Pattern: a correction sweep that fixes the clause it was handed and not the file it lives in
**Issue**: M1's eighth verification gate re-verified all 33 tasks and held 11. Nine of the eleven are the *same defect*: a task corrected the exact line its finding named and left an identical or dependent claim standing elsewhere — usually in the same file, twice in the same paragraph. `P0-M1-FIX-13` re-tensed `BASELINE.md`'s fact 2 and left the identical present-tense claim in the lead paragraph six lines above it. `P0-M1-FIX-14` recorded the repo revisions in `BASELINE.md` while naming `baseline.json` "the better home" and never touching it. `P0-M1-FIX-19` corrected `fsutil_test.go` while `NOTES.md:95` — written by this same run — named `state-atomicity.md` alongside it. `P0-M1-FIX-23` added two prose sections and updated neither the page's own §Usage index nor `docs/directory-structure.md`, which its own text required. `P0-M1-FIX-25` refreshed the five SHAs it was looking for and never enumerated the four files it claims it rewrote in place, leaving four dangling. `P0-M1-FIX-21` recorded the anti-pattern in `NOTES.md` and restated the withdrawn relation eight lines later at `:213`.
**Root Cause**: a finding is written as a *locator* — `file:line`, plus the wrong sentence — and an agent optimising for a clean, minimal, reviewable diff treats the locator as the scope. Nothing in the task text asks "where else does this claim appear?", and nothing mechanical checks: `belmont validate` is clean, the build is green, and a documentation claim has no test. So each round closes one instance and mints the next, and the milestone converges at roughly one instance per round against a defect population that is file-shaped, not line-shaped.
**Prevention**: when a finding is that a **claim** is wrong (as opposed to code being wrong), the unit of repair is the **file pair**, not the line — `grep` the claim's distinguishing phrase across the repo before writing the fix, and state in the completion note which occurrences were found and which were deliberately left. The verification gate should mirror it: verify the document, not the clause. `P0-M1-FIX-26` is deliberately written as one sweep over `BASELINE.md` + `baseline.json` covering five findings at once for exactly this reason — five more single-clause rounds is the measured alternative, and it is what the previous seven rounds already cost.
**Relation to the entry below** (*"six rounds of clause-scoped fixes, because the unit of verification was wrong"*, `P0-M1-FIX-21`, round 7): that entry is this one at a smaller radius. It found the pattern **within one section of `CENSUS.md`** and prescribed *"verify the paragraph, not the clause"*. Gate 8 found the identical failure across **six different tasks and five different files**, including three that had already adopted the paragraph rule — so the radius is wrong again, not the rule. The escalation is: **verify the document, not the paragraph**, and for a claim that can be grepped, verify the repository. Do not treat these as duplicates; the second is evidence that the first's remedy was correctly applied and still insufficient.
**Source**: M1 / gate 8 `/belmont:verify`, 2026-08-19 — 33 tasks verified, 22 promoted, 11 held, 7 follow-ups minted

### [2026-08-19] Pattern: the orchestrator's own coverage claim was wrong, and every agent repeated it
**Issue**: the verify orchestrator measured the toolchain gates up front and told all five sub-agents *"`staticcheck` is not installed on this machine — note as a coverage gap"*. Four agents dutifully recorded the gap. The fifth checked and found `staticcheck 2026.1` at `$(go env GOPATH)/bin/staticcheck`, and `staticcheck ./...` exiting 0.
**Root Cause**: the orchestrator probed with `command -v staticcheck`, which answers "is it on **this shell's** PATH", not "is it installed". `$(go env GOPATH)/bin` is not on the non-interactive shell's PATH, so a Go tool installed exactly as `AGENTS.md` prescribes (`go install honnef.co/go/tools/cmd/staticcheck@latest`) reads as absent. The failure then **propagated by authority**: it was stated as measured fact in five prompts, so four agents had no reason to re-derive it, and a false coverage gap nearly reached the report as a finding.
**Prevention**: probe Go-installed tools at `$(go env GOPATH)/bin/<tool>` before concluding they are absent. More generally — anything the orchestrator asserts as measured becomes unfalsifiable for every agent downstream, so a cheap wrong measurement is more expensive than no measurement. Say "unverified" rather than asserting a negative, and prefer the phrasing that invites a check ("I could not find X; confirm before relying on it") over the one that closes it ("X is not installed").
**Source**: M1 / gate 8 `/belmont:verify`, 2026-08-19

### [2026-08-19] Pattern: six rounds of clause-scoped fixes, because the unit of verification was wrong
**Issue**: `P0-M1-FIX-21` is the sixth consecutive correction of one defect — a sentence asserting a *relation between* two measured figures, beyond what the figures support. `FIX-6` → `FIX-8` → `FIX-9` → `FIX-10` → `FIX-11` → `FIX-21`, all in one section of `CENSUS.md` plus its copies. The sixth was found **inside a correction that had itself already passed two verification rounds**.
**Root Cause**: Every round was scoped to the clause that was objected to, so each fix wrote a *new* relational sentence next to the old one and shipped it with only that sentence checked. The figures were never the problem — all of them re-derive exactly, repeatedly, at real cost. The instrument was aimed at the wrong unit: a clause can be true in isolation and false against the paragraph it sits in, and "8 registers balance two non-zero terms" contradicted a clause **eleven lines below it** that two rounds had already verified.
**Prevention**: **Verify the paragraph, not the clause.** When a fix edits a sentence that relates two measurements, the acceptance criterion is that every *other* relational claim in the same section still holds against the new wording — cheaper than one more round, and it is what would have caught instances 3 through 6 in one pass. Two supporting rules: prefer restating what the arithmetic supports and stopping (the FIX-21 replacement asserts equality and refuses to characterise the terms individually, because no per-register measurement of them exists); and when a correction cannot be discharged without a measurement nobody has taken, say that rather than inferring it.

### [2026-08-18] Pattern: a self-pacing loop that trusts its own prompt acts on stale state
**Issue**: A `/loop` firing carried a state snapshot four rounds out of date — it described a completed task as just-dispatched and five verified tasks as still `[x]`. **Prevention**: A recurring prompt must carry **pointers to state, never copies of it** — the file to read and the command to run, not the values. ### [2026-08-18] Pattern: the batch documented a pattern and then reproduced it three times

### [2026-08-18] Pattern: a remote-tracking ref was read as if it were the remote

**Issue**: The 2026-08-19 re-scope revised `BASELINE.md` three times across three commits and never touched `baseline.json`, which still instructs a reader to run the withdrawn, PRD-prohibited capture method verbatim — and `BASELINE.md`'s own numbered fact 2 still asserts "neither repo has ever recorded a metric" two sections above the six records it now documents.

Where a document names a machine-readable companion, treat the pair as one artifact: neither is correct until both are, and a re-scope that touches only one is incomplete by definition.

### [2026-08-19] Pattern: a baseline pinned its instrument but not its subject
**Issue**: `BASELINE.md` records the Belmont version, its commit, the binary path and the Go toolchain — and not the revisions of the two repositories it measured, nor the fact that "the estate" means 2 repos of 5 (43 of 82 live registers). ### [2026-08-19] Pattern: a task's text was copied into shipped source as its own evidence

### [2026-08-19] Pattern: wrapping a writer removed a serialisation guarantee the standard library was providing for free
**Issue**: `tailWriter` has no mutex and never needed one: `os/exec` dedups `Stdout` and `Stderr` to a single pipe and a single copy goroutine when the two are `interfaceEqual`. `attachUsageCapture` wraps `Stdout` to sniff token usage, which breaks that equality, so two goroutines now append to `tw.buf` and `tw.lineBuf` concurrently.
**Root Cause**: The safety property lived in a library implementation detail, not in the type that depended on it. `tailWriter` never documented "single-writer only", so nothing warned the implementer that changing *what* was assigned to `cmd.Stdout` changed *how many* goroutines would call it. The suite drives `tailWriter` directly and never through a real `exec.Cmd`, so `-race` cannot see the path — the bug is invisible to precisely the tool that would name it.
**Prevention**: State concurrency expectations on the type, not in the caller — a writer handed to `exec.Cmd` should be safe for concurrent use, full stop, because whether it receives one goroutine or two is a property of code somewhere else. When a change alters what is assigned to `Stdout`/`Stderr`, re-ask how many writers the assignment implies. And where a race is only reachable through a real subprocess, add the test that spawns one; a green `-race` over unit tests is evidence about the tests, not about the path.
**Source**: M1 / `P0-2` → `P0-M1-FIX-18`, `P0-M1-FIX-19`

### [2026-08-19] Pattern: robustness was added at the level the bug was found at, not at the level the traversal repeats
**Issue**: `P0-M1-FIX-7` made an unreadable census *root* a reported failure instead of a silent skip. `extract.go:220-228` still swallows an unreadable *register* into `NoRegisterDirs`, undercounting `LiveRegisters` while `coverage_complete` continues to report `true` — the exact honesty guarantee FIX-7 was written to install.

But `runCensus` is a two-level traversal, and the same error-swallowing idiom appears at both levels; the fix was scoped to the reproduction rather than to the idiom. This is the `progress-md-parsing` lesson from `CLAUDE.md` in a new place: a half-converted set of readers is worse than an unconverted one, because the surviving copy is now covered by a guarantee that does not reach it.
**Prevention**: When fixing an error-handling idiom, grep for the idiom rather than fixing the site — and where a traversal nests, check every level before claiming the property. If the fix introduces a *coverage* flag, that flag is now a claim about all levels and must be wired to all of them.
